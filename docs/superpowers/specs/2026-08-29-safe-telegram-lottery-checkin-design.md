# 安全 Telegram 抽奖与每日签到设计

## 1. 适用范围与默认拒绝

本设计只适用于已经取得管理员明确许可、且在全局 `TARGET_GROUPS` 中显式配置的 Telegram 群组。系统只解析、扫描和执行这些目标群；不会根据账号已加入的其他群、转发来源、搜索结果或链接扩大范围。所有配置对全部目标群全局生效，不支持按群覆盖。

除本规范列出的受控动作外，系统一律不自动执行：加群或关注、转发、私聊、打开外部网页、URL/Web App/登录、支付、验证码、答题、投票、消息反应、提及他人、收集手机号或邮箱。所有生产 Telegram 调用只能经受控 sender 发出；测试必须使用 fake/mock，并隔离 Telegram、AI 和其他网络服务。

## 2. 时间、每日批次与签到

- 所有自然日、窗口与截止判定均使用 `Asia/Shanghai`；时钟、随机数与等待均可注入以支持确定性测试。
- 启用运行窗口时，当天首次进入任一窗口才创建每日批次；未启用窗口时，启动即创建。批次创建时固化 `TARGET_GROUPS` 解析得到的群快照，当天之后新增、删除或重新配置的群都不加入该批次。
- 每个快照群在每个上海自然日最多尝试一次签到；重启只补未完成的快照项。签到失败当天不重试，并阻止该群当天的普通参与，但不阻止其抽奖扫描和抽奖参与。
- 恢复判定只接受本账号发送的、非回复、顶层且精确为“签到”的文本；抽奖相关消息和回复一律不得作为签到恢复依据。来源仍有歧义时可再发送一次，但必须记录歧义审计。
- 签到复用持久化的发送预留与确认，并计入普通参与的 `DAILY_LIMIT`。

## 3. 扫描、识别与 AI 外发

- 扫描仅生成不可变消息快照和发现记录，绝不直接执行 Telegram 动作；一批消息全部识别并持久化成功后，才在同一事务推进扫描游标。
- 无游标冷启动时，以当前最新普通消息 ID 建立基线，不回溯普通历史；只扫描上海当日仍置顶的消息。离线恢复时，普通消息最多检查上线前最近一小时；无截止时间的候选也只允许来自这类一小时增量或上海当日置顶。
- 规则优先识别抽奖。只有规则无法确定时，才可在 `AI_ENABLED=true` 且用户已明确授权向所配置 AI 服务外发的前提下调用 AI。
- 外发给 AI 的内容严格限于消息正文、必要的上下文和按钮元数据；不得发送媒体二进制、Telegram 凭据、session、数据库、callback 原文之外的敏感状态或用户不必要的信息。纯媒体只记审计，不能自动产生抽奖提醒。
- AI 只能返回固定结构化结果 `is_lottery`、`confidence`、`summary`、`deadline`、`required_actions`、`reason`，且置信度至少 `0.80` 才能继续规划。AI 不得生成 Telethon 调用、代码、自由参与文案或任何执行参数；关闭、超时、非法 JSON 或低置信度时，严格规则结果可继续，否则转人工。

## 4. 稳定身份、发布者信任与去重

- 群状态以 Telegram 稳定 `peer_id` 为主键，配置 URL/用户名仅是别名；启动时必须事务化解析并迁移旧 URL 状态，失败即拒绝启动自动任务。
- 自动执行前必须重新查询发布者信任。仅发布者为 owner、admin 或 bot 且权限查询成功时可自动执行；普通成员、权限未知或查询失败一律为不可信并转人工。
- 永久消息键 `peer_id + message_id` 优先阻止同一消息重复处理。
- 基础指纹为 Unicode NFKC 规范化正文、按钮行列顺序、按钮显示文本、按钮种类和 callback data 的 SHA-256 摘要；基础指纹不含群 ID 和截止时间。
- 全账号跨群去重窗口为七日：基础指纹相同且截止时间相同即视为重复；任一截止未知时也视为重复；两个明确且不同的截止时间视为新一期。去重不因跨群而失效。

## 5. 动作白名单与执行前复核

自动计划只允许引用原消息中的以下动作：

1. 恰好一个明确参与含义的 callback 按钮；或
2. 符合文本白名单的固定顶层文本或固定回复文本。

固定文本最多 32 个 Unicode 字符，只允许中英文、数字、空格、常见标点、emoji 和 `+1`；禁止 URL、提及、手机号、邮箱、换行、控制字符及任何未白名单内容。URL、Web App、登录、支付、多个可能参与按钮、可选加码或任一额外非白名单条件，都必须使整条候选转人工，不能先执行基础步骤。

计划动作类型仅为 `CLICK_BUTTON`、`SEND_TEXT`、`REPLY_TEXT`。每个动作保存原消息签名；执行前必须重新读取原消息、按钮、群实体和发布者并重新规划。消息删除、内容或按钮变化会使旧计划标记为 `SUPERSEDED`，并重新完成信任、白名单、指纹、截止、配额和冻结检查。AI 输出绝不成为执行参数。

## 6. 风控、配额、结果不确定与停止

- 所有 Telegram 外部动作在调用前必须经 SQLite `BEGIN IMMEDIATE` 成功预写；持久化不可用或确认失败时 fail closed，停止后续外发，绝不猜测重做。
- 首个外部动作前，在同一事务检查并占用每群及全账号上海当日抽奖配额。扫描、重复、人工提醒及发送前发现已参与不占配额；`PARTICIPATED`、已参与、`PARTIAL`、`RESULT_UNKNOWN` 和调用已发出后的明确失败均不退款。
- 全账号只有一个抽奖 Telegram 动作流；不同抽奖之间使用可注入的随机等待，同一抽奖的安全步骤连续执行。停止时取消尚未进入 Telegram 调用的任务；当前调用返回后不开始下一步。
- callback 超时或断连为 `RESULT_UNKNOWN`：不重试、不退款，只冻结该群的抽奖执行器，不冻结签到或普通参与。用户打开该提醒时解除该群抽奖冻结并记录审计，但不得改变原参与状态。
- 单实例锁覆盖整个后台生命周期，锁键由账号稳定摘要和规范化数据库绝对路径派生。Windows 锁记录 PID、进程创建时间与持有者信息，避免 PID 复用误判；第二实例必须在连接 Telegram 前拒绝启动。SQLite 幂等不能替代单实例协调。

## 7. 持久化、可见性、清理与已接受风险

SQLite WAL 保存 schema 版本、每日批次、任务、扫描游标、抽奖、动作、配额、冻结和审计。迁移必须幂等；升级失败时不得继续使用数据库。Dashboard 只显示脱敏摘要，支持分页告警、消息深链或群会话降级、SSE 事件和停止状态。

历史清理只能由人工在 manager 为 `IDLE` 或 `STOPPED` 时发起；运行、启动或暂停中均拒绝。清理以用户选择的上海自然日为边界，在单一事务中删除该日以前的抽奖详情、动作、相关审计、消息幂等键与内容指纹，并返回各类删除数；状态在校验后发生变化也必须拒绝，防止 TOCTOU。

已接受风险：清理移除消息键和跨群指纹后，旧置顶或重投消息可能再次被识别、提醒或参与；因此界面必须二次确认并明确提示该风险。打开原消息只表示用户已打开查看，不表示系统已核验其真实性、有效性或结果。

## 8. 配置与仓库卫生

`.env.example` 必须列出所有全局配置并仅使用占位符和安全默认值：AI 默认关闭；已确认的每日签到、抽奖总开关和每日置顶抽奖扫描默认启用（`true`），但功能开关不构成授权，运行前仍须由操作者确认 `TARGET_GROUPS` 中每个群均已获许可。不得提交 `.env`、Telegram session、数据库、`state/`、AI API key、手机号、callback 原始敏感数据或其他凭据。

`.codegraph/`、`.venv/`、Python/测试缓存及敏感运行状态必须被 `.gitignore` 忽略。`.hermes/plans/` 是项目实施资料，应保留跟踪；不能因本地工具目录规则被误忽略。
