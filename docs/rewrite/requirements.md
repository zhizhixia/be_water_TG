# Be Water TG 新版需求与合理性审查

> 状态：四项核心方向已获用户批准，进入主代理独立实施；本文件不代表新版已经实现。
> 批准内容：自然接话与冷场补充；每群分别开关聊天、签到、抽奖；签到失败不阻断其他业务；抽奖仅执行明确白名单动作。
> 配置补充：各群任务开关独立，概率、时段及额度使用全局参数。此前“全群统一功能开关”的建议由本次批准内容取代。
> 提炼日期：2026-10-18。执行者：主代理；需求提炼与实现不使用子代理。
> 依据：当前真实工作树（`c0eb6a7` 加上未提交修复），不是远端标签的纯净版本。
> 最终目标：实现本文批准后的全部用户功能，包括 Web 前端、后端、数据迁移和本地发布。最终才由只读子代理比较新旧实现。

## 一、从仓库提炼出的真实目标

在操作者明确取得管理员许可的 Telegram 群中，让一个本机账号低打扰地参与有内容的讨论；在冷场时有限度地主动发言；按需执行每日签到与安全、简单的抽奖参与。操作者通过中文本地网页看清程序现在在做什么、为什么没发言、需要处理什么，并能可靠暂停或停止。

成功不等于发言数量最多，也不等于所有抽奖都自动完成。成功是：相关时能接话、不重复刷屏、不会突破范围和额度、不会因附属任务拖死聊天、不会丢失会话和状态、遇到不确定动作能明确交还人工。

### 需求来源的置信层级

- **已有目标**：来自历史设计与真实用户入口，优先保留。
- **实现现状**：代码现在具有的行为，可能是缺陷，不能自动升级为需求。
- **本轮建议**：为消除冲突或补齐闭环而提出；本文件获批后才作为新需求。

## 二、合理性审查：哪些保留，哪些改变

| 问题 | 依据与影响 | 新需求建议 |
|---|---|---|
| 把“保留全部代码行为”当“保留全部功能” | 旧实现存在失效参数、两套界面和仅在测试里运行的协调内核 | 保留用户能力，不保留偶然实现与无效开关 |
| 普通聊天被签到失败连带阻断 | 旧抽奖设计明确这样规定，但与持续参与讨论目标存在业务耦合 | **建议三条业务独立**：签到失败不封锁普通聊天；授权撤销、明确投诉、数据库失败和限流等共享安全边界仍必须约束相关外部动作 |
| 新增功能缺项时默认开启 | 旧示例与模型中签到、抽奖默认开启；本机目前显式关闭 | 新版新增自动外发默认关闭，迁移尊重原显式选择，不因升级或保存其他项自动开启 |
| 网页读写丢失抽奖配置 | 隔离复现：GET 不含 `lottery_enabled`，将响应原样 POST 后两个关闭开关均变 `True` | 配置必须形成完整、类型严格、无副作用的读写闭环；不修改字段保持原值 |
| 把 AI 最近说过的话仍在上下文视为“无人回应” | `src/ai_sender.py:26–48` 只比较文本是否仍出现 | 依消息 ID、时间、作者和后续有效活动判断，不能依文本残留判断 |
| 任意新消息都取消候选 | `ui/send_loop.py:540–556`，活跃群持续难以发言 | 新消息触发相关性重评估；仍属当前话题可重生成，过时或风险变化才取消；不丢掉新触发消息 |
| 多次轮询抽概率造成重复机会 | 当前循环可重复评估相似冷场或内容 | 同一触发消息/同一冷场事件只抽一次概率；重新生成不重复抽取获胜机会 |
| 每日最多一次与未知结果时允许再签到冲突 | 历史设计允许有歧义时再发一次 | 选择保守的“至多一次自动外发尝试”：调用已发出而结果未知时不自动重发，不声称能保证恰好一次成功 |
| 抽奖固定文本只存在模型里 | 当前规划先要求 callback，正文“回复”又被整体拒绝 | “全部功能”应补齐**独立的固定顶层文本/固定回复**路径，且只从原消息的确定性白名单格式提取，不允许 AI 自由生成参与词 |
| 仅维护按钮关键词黑名单不能证明附加条件安全 | 未知语言、隐含条件、可选加码可能绕过关键词 | 白名单条件匹配不完整一律人工；宁可漏自动参与，不猜测条件已经满足 |
| 七日去重与实际仓储行为不一致 | `LotteryStore.is_duplicate()` 未按七日过滤；`created_at` 未在发现时可靠填写 | 持久化发现时间并按七日窗口查询；同一消息键独立永久去重，清理除外 |
| 扫描上限与游标推进导致漏消息 | `get_messages_after()` 取最新有限批次，生产再推进最大 ID | 按游标正序分页，完整处理每页后原子提交；离线恢复限制最近一小时，不能把批次上限当永久丢弃旧消息 |
| 打开消息等于解冻未知结果 | 旧设计规定 open 同时解冻，但打开网页不代表已检查 | **建议拆为两个动作**：打开原消息不解冻；用户阅读风险后明确恢复该群抽奖；不改写原 UNKNOWN 终态 |
| 只按截止清理历史 | `cleanup_before()` 使用 `deadline < cutoff`，无截止项无法按发现日期清理 | 按上海“发现日期”清理，保留清理边界当日及以后的记录；危险后果二次确认 |
| 保存成功被误读成后台热生效 | 实际后台持有启动时配置快照 | 允许运行中保存“下次生效”的配置，但清楚显示待重启应用；安全停用开关必须立刻阻止新动作；凭据/授权群变更需先停止 |
| 继续维护旧 Flet 前端 | README 与生产入口均以 Web 为主，旧 Flet 仍带额外测试和弃用依赖 | **建议 Web 为唯一正式前端**；完整保留相应用户能力，不重写第二套 Flet |
| “反检测”与低打扰混为一谈 | 多个参数仅存在配置和旧界面，当前生产循环不消费 | 不做隐藏自动化身份或规避平台风控；只保留有业务含义的等待、节流与平台要求的冷却；旧无效字段只迁移告知 |

以上是本轮主代理审查建议，不冒充用户此前已经批准的新偏好。

## 三、完整功能需求

### R01｜本机启动、首次设置和账号连接

- Windows 单用户、单 Telegram 账号；源码和完整目录发布包均可启动。
- Web 仅监听 `127.0.0.1`，默认端口保留 `5000`；端口冲突明确报错，不杀占用进程、不暗改端口。
- 没有配置时显示首次设置流程；网页资源可用，业务动作不可用；单纯打开网页或保存配置不得登录 Telegram。
- 只有用户点击开始后才尝试连接；优先复用 session；需要验证码时在当前本机会话中提交。两步验证账号需要对应密码步骤，不得持久化验证码或两步验证密码。
- 登录错误、超时、密码错误、会话失效、用户停止均有中文状态与可恢复入口，不得卡死为“正在启动”。
- 后台账号/状态库互斥锁必须在连接 Telegram 之前取得；服务实例锁和后台任务锁各司其职，异常退出可安全恢复。

### R02｜配置完整、安全、可理解

- Telegram 凭据、代理、授权群、参与策略、AI/TXT、工作时段、签到、抽奖开关与额度均在网页可编辑，不出现“配置存在但界面没有”的半成品。
- 读取配置不返回 API Hash、AI Key 明文，只返回“已设置”；空输入表示保留，清除需要独立明确动作；暂停 AI 不应删除它的密钥。
- 数字、布尔、地址、范围与字段关联由后端严格校验，不接受字符串 `"false"` 被当成真或非法值被无声替换为默认。
- 配置保存原子化，写失败不报成功；读→改一项→写→再读，其他配置与安全开关不变；多行提示词、引号、等号能往返。
- 未提供新字段使用安全默认，不扩大外部行为；已有显式关闭保持关闭。
- 使用当前既有依赖与协议；不新增第三方服务、云控制面或必须在线的前端 CDN。

### R03｜授权群与稳定身份

- 操作者显式维护群列表；兼容 `@username`、`t.me/username`、完整链接，支持逗号、中文逗号、换行并规范化去重。
- 不自动发现加入群，不自动处理账号所有会话；私密群仅在已有成员身份可解析时使用，不能为解析而执行加入操作。
- 拒绝把单聊、机器人私聊、非群频道等错误实体当成授权群；错误明确对应到输入项。
- 数据以稳定 marked peer ID 为准；用户名/URL 是别名；Telegram 交互使用已解析的 typed InputPeer。
- 同一群的不同别名不双计数、不双签到、不重复扫描；显示群标题/链接，不能仅显示难理解的负数 ID。
- 从授权范围移除后，不允许旧批次、候选或队列继续向该群外发。
- 每群分别开关聊天、签到、抽奖；概率、时段及额度参数全局统一。每群暂停/恢复、运行状态和 TXT 映射仍保留。

### R04｜运行、暂停、恢复、停止

- 具有未运行、启动中、等待认证、运行中、暂停中、已暂停、停止中、已停止、故障状态的清楚语义。
- 并发点击开始只能启动一个后台实例；失败返回明确原因。
- 暂停后不启动新外部动作；已发出的网络调用不能虚构撤回，但返回后不能继续下一动作；观察与必要状态查询可继续，不能因暂停丢掉安全信号。
- 停止可中断验证码等待、普通候选等待、队列间隔和 FloodWait 等待，清理未开始任务并断开客户端。
- 恢复重新校验候选和任务，不补发过时消息；重启不恢复普通聊天未发送候选。
- 页面断开不停止后台；页面必须显示“连接丢失，后台状态未知”，不能假装后台已停止或已配置。

### R05｜上海时间与统一调度

- 所有自然日、配额、签到、清理边界使用 `Asia/Shanghai`；相对延迟使用单调时钟。
- 支持原有上午/下午两个窗口；输入合法且区间有序。不新增跨夜复杂排班，除非另行确认。
- 窗口外不发送普通聊天、签到或抽奖动作；可只读观察，避免回到窗口时使用陈旧上下文。
- 每次实际外发前重新检查窗口、暂停/停止、授权、配额和相关冻结；不能只在一轮开始时检查一次。
- 跨日自动刷新额度和每日批次；跨窗口、断线恢复、系统时间变化不能触发重复任务。
- 某群慢请求、抽奖队列等待或 AI 请求不能长期阻塞其他群；全账号外发串行且公平调度。

### R06｜自然参与讨论

- 首次启动只建立观察基线，不把普通历史消息当新话题轰炸。
- 新增非本人、有实质内容的消息形成问题或讨论候选；表情、低信息寒暄、不相关内容跳过。
- AI 可用时辅助语义分类，失败有保守确定性降级；分类结果只影响参与，不扩大外部权限。
- 问题/普通讨论使用不同参与概率，默认沿用 70%/15%；同一触发只决策一次，不靠重复轮询提高概率。
- 冷场默认 10 分钟后允许有限度主动发言；本账号发言后没有其他人有效活动时，不接连自言自语。
- 发送前等待默认 20–90 秒；期间有新消息时重新判断话题仍否相关，而非任何变化都永久丢弃候选。
- 普通参与保持独立群消息；不新增普通聊天自动提及或任意引用回复；抽奖固定回复是单独受限动作。
- 不假装是真人、不编造身份经历，不以“自然”为名绕过群规。

### R07｜AI 与 TXT 生成闭环

- AI 使用现有 OpenAI 兼容接口、可配地址/模型/提示词/上下文数量/采样参数/超时。
- 启用前清楚说明会向操作者选择的服务发送哪些群聊文本；不会发送凭据、session、数据库或媒体二进制。
- AI 返回跳过、不相关、过长或重复内容时不强行换一条 TXT 发送；网络失败等不可用情况才允许 TXT 降级。
- TXT 支持共享消息库与每群映射；允许在网页查看和编辑受控用户消息文件，显示消息数量、空文件和错误。
- 新编辑格式采用一行一条，保留句中中英文逗号；旧逗号分隔文件按旧语义导入并提供预览，不能无声改变原消息。
- 只能访问运行数据目录受控 TXT 或明确内置资源；拒绝绝对路径、穿越、链接逃逸、超限和非法编码。
- 只有发送并可靠记账后才提交 AI 自身历史和重复历史；不因生成过但取消而永久封锁内容。
- 最近去重记录重启后仍有效；候选只在内存，已发送记录在持久化账本。

### R08｜普通参与限额与安全停发

- 默认每群上海每日 30 条；签到计入同一文本额度；抽奖配额单独统计，但抽奖文本不得绕过平台与统一节流。
- 额度是上限，不是每日必须完成的目标；达到上限到次日恢复，不能手动恢复绕过当日额度。
- 本账号发言后两个完整冷场窗口仍无有效回应，该群普通参与自动暂停到次日；明确区分“无人回应”与“旧文本仍在上下文”。
- 指向本账号的明确投诉、管理员警告触发严重安全暂停，阻断该群所有自动外发，人工检查后才能恢复；旁观提及仅审计。
- Telegram 限流按要求冷却，不缩短、不换账号绕过；受影响动作与范围清楚显示。
- 网络提交是否成功无法确定时不盲目重试；额度保守占用并展示未知状态。
- 数据库故障或发送后确认失败，停止新外发并告警，不能为了看起来继续运行而丢账。

### R09｜每日签到

- 可独立启用/关闭；默认关闭；开启后每个当日授权群发送一次顶层精确“签到”。
- 当天首次允许窗口创建批次；跨日自动创建；同一天新增群次日进入签到批次，移除群立即失去发送资格。
- 每群每日最多一次已进入外部调用的自动尝试；停止前未进入调用的任务可恢复。
- 重启按任务账本与本人当日精确顶层“签到”核验，抽奖参与文本和引用回复不能冒充已签到。
- 结果未知保守记录、无需程序猜测重发；页面显示成功、失败、已尝试未知、等待窗口与停用。
- **本轮建议**：签到失败只告警，不连带停止普通聊天或抽奖；共享安全暂停仍阻断签到。

### R10｜抽奖扫描

- 可独立启用/关闭，默认关闭；支持当日置顶扫描子开关与可配扫描间隔，沿用 15–1440 分钟合法范围。
- 无游标冷启动建立最新普通消息基线，不追溯普通历史；只检查上海当日仍置顶的消息。
- 有游标时按 ID 正序分页；离线恢复普通消息仅检查最近一小时；一页成功持久化后推进该页检查点，失败不跨过未处理消息。
- 上限用于单页资源控制，不能永久跳过超过单页的消息；下一轮从未完成位置继续。
- 置顶枚举受限/失败显示“不完整”，不能把截断结果报为完整；单群失败不悄悄停止全部观察。
- 展示每群最近扫描、下次扫描、是否降级、错误和发现数，不只显示后台原始日志。

### R11｜抽奖识别、信任与去重

- 规则优先；不确定时才向已授权 AI 服务发送必要正文和安全按钮元数据。
- AI 输出固定 schema，置信度至少 0.80；非法、未知、低置信度转人工，不能授权动作。
- 自动执行仅限当前 owner/admin/bot 发布且角色查询成功；仅“看起来是机器人”不算可信，管理员身份也不证明抽奖安全。
- 截止有明确时区时按绝对时间验证；“今晚”等表达必须绑定消息时间、时区与确定性证据，无法验证转人工；AI 不能凭空赋予更宽截止。
- 无截止候选仅限最近一小时增量或上海当日置顶来源。
- 同一 peer ID + message ID 长期去重；规范化正文与按钮指纹跨群七日去重；同内容、不同明确截止可视为不同期，任一截止未知时保守去重。
- 必须保存发现时间、截止、来源、识别理由、参与状态与提醒状态；不保存原始 callback 到普通日志/前端。

### R12｜抽奖安全执行，含固定文本

- 支持三种明确互斥的单一计划：一个参与 callback；一条固定顶层文本；一条针对原消息的固定回复。
- 固定文本必须从原消息的明确格式原样提取，最多 32 个 Unicode 字符；不接受 AI 自由创作。URL、提及、手机号、邮箱、换行、控制符拒绝。
- 一个抽奖有多种参与方式、组合动作、可选加码、任何未知条件，整条转人工，不先执行容易的步骤。
- 加群、关注、转发、私聊、URL/Web App/登录/支付、验证码、答题、投票、反应一律不自动执行。
- 执行前重新查询当前授权、群实体、发布者身份/权限、正文、按钮、截止、已参与状态、去重、配额与冻结，再重新规划；变化后旧计划失效。
- SQLite 成功预写动作与占用额度后才进入 Telegram；尚未发出时取消可撤销预留，已进入外部调用的未知或失败不得当作“未发送”退款重试。
- callback 超时/断连记 UNKNOWN，不重试、不退款，只冻结对应群抽奖；普通参与不因抽奖特有未知结果冻结，除非共享安全条件触发。
- 每个动作结果能在网页和审计中核对，不把按钮返回的模糊字符串一律显示成功。

### R13｜抽奖额度、提醒与历史

- 默认每群每日 10 次、全账号每日 30 次，保持全局统一配置；动作间隔默认 20–60 秒。
- 发现、人工提醒、重复与发送前确认已参与不占自动执行额度；配额和动作预写在同一事务。
- 网页有独立抽奖工作区：待处理提醒、执行历史、冻结群、扫描状态；列表分页并同时显示总数。
- “打开原消息”由用户点击触发，只打开经过校验的 Telegram 链接；公开群、私有超级群和无法构造消息链接的群分别正确降级。
- **本轮建议**：“查看提醒”与“解除抽奖冻结”分开；解除前用户确认风险，原 UNKNOWN 状态保留且旧动作不重试。
- 历史清理仅空闲/停止可用，选择上海日期、显示影响范围、二次确认，再在一个事务中删除关联历史；运行状态并发变化时拒绝。
- 提醒清理会移除部分去重信息、可能再次发现旧内容；明确提示，不声称永远不会重复。

### R14｜持久化、兼容与升级

- 所有运行数据仍集中在 `%LOCALAPPDATA%\BeWaterTG`：配置、session、SQLite、用户消息、轮转日志与备份。
- 旧 `.env`、代理、授权群、AI 配置、TXT 内容、登录会话、计数、暂停、任务、去重与审计不因重写丢失或重置。
- 在副本上演练 schema 升级，幂等、有版本、失败回滚；无法可靠映射的状态保守阻断并告知，不能清空数据库伪装升级成功。
- 兼容旧 URL 键、错误类型/raw 群键的已有记录时要独立核验真实实体，不能猜测合并造成跨群污染。
- 不恢复旧未发送候选；旧已发出但未确认的记录保持保守额度，不伪装成成功或自动重发。
- 先备份后迁移，不覆盖不同来源的现有目标；原代码目录与原始数据保持可还原。

### R15｜完整中文 Web 前端

- **建议唯一正式前端为 Web**；不重建旧 Flet，也不引入新的大型前端框架。
- 所有标签、状态、错误、空状态、帮助与危险确认中文；API ID、AI、Telegram 等专有名词可保留。
- 全局状态和开始/暂停/恢复/停止始终可见；不能让多个面板、弹层和返回栈掩盖主任务。
- 核心入口：运行概览；授权群；普通参与；签到与抽奖；AI 与消息库；安全与审计；连接与设置。具体导航合并可在原型阶段调整，但每项能力必须有可到达入口。
- 概览分开显示普通消息、签到、抽奖尝试与未知结果，不把全历史或本次会话计数冒充“今日发送”。
- 群表展示真实标题、链接、今日额度、三类任务状态、最近决策、暂停原因和必要人工操作。
- 所有配置具有加载、校验、保存、失败、未保存提示和生效时机；前后端必须 round-trip 一致。
- 抽奖分页、打开、恢复、历史清理全接真实 API；TXT 编辑/校验全接受控存储；禁止按钮摆设和硬编码成功态。
- SSE 断开有明显离线提示；重连先取完整快照再续事件，处理服务重启导致的序号重置，不把旧状态当现在。
- 以 1440×900 与 1280×800 桌面视口验收；窄窗口可正常操作，暂不承诺手机端完整产品适配。
- 键盘、焦点、原生表单语义、确认框与无障碍标签不能为简化而省略。正式实现前给两套相同功能、不同信息布局的静态原型，避免盲目大改。

### R16｜本机服务安全与隐私

- 回环监听不等于任何网页都可驱动它：写操作检查合法 Host/Origin 与会话防跨站标识，不开放通配跨域。
- 群消息和 AI 内容均不可信：前端文本安全渲染，不使用消息内容执行 HTML/JS；AI 不能获得工具执行权。
- 日志、SSE、异常响应和发布包不得包含密钥、验证码、两步验证密码、原始 callback 或 session 内容；手机号仅必要设置处展示，不广播。
- 开发与自动测试使用临时运行目录、阻断 Telegram/AI 真实外发；本轮重写不授权真实账号发送或点击。

### R17｜Windows 交付与维护

- 保留 Python 3.11、锁定依赖、`uv` 命令、启动脚本和完整目录 ZIP/EXE 发布能力。
- 发布包包含模板、静态资源、占位配置与消息样例，不包含真实运行数据、测试私密归档和开发工具目录。
- 实际构建并审计 ZIP 清单；隔离运行目录验证启动、健康、页面资源、单实例、退出与端口释放。
- 无法构建、依赖下载受阻或真实外部验证未执行时如实记为缺口，不能用脚本的 Mock 测试替代真实打包。
- README 与 AGENTS.md 只描述真实入口和已实现能力，不保留两套相互矛盾的运行说明。

## 四、不做的事

- 不自动加群、群发现、私聊营销、反风控、账号池或多账号轮换。
- 不新增手机 App、云托管、多用户权限、群组独立策略、插件平台、工作流编辑器。
- 不为了“全部重写”重造 Flask、Telethon、SQLite 或密码存储协议。
- 不追求保留失效 `ANTI_DETECT`、模拟思考、随机跳过等旧设置的表面存在；有实际作用的等待/节流合并为清楚的业务设置，迁移报告列出变化。
- 不为了测试数好看保留或重写整个旧 Flet 测试层；但任何旧测试对应的真实用户行为都必须映射到新验收，不靠删除失败用例制造全绿。
- 不提交、推送、发布线上 Release，也不迁移真实运行数据或做真实 Telegram 动作，除非用户另行明确授权。

## 五、验收不是“代码写好了”

1. R01–R17 每项必须映射到实际入口、实现文件和可运行证据；没有入口或只有 Mock 空壳记未完成。
2. 同一套独立业务场景分别运行旧基线与新版；旧版失败是已知缺陷，不为照顾旧版而删反例。
3. 离线证据至少覆盖配置全往返、安全开关不复活、身份一致、自然参与、AI/TXT 降级、跨日/跨窗口、签到去重、抽奖分页/七日去重/固定文本/未知结果、暂停停止竞态、持久化故障、迁移与清理。
4. 浏览器实际操作前端，使用匿名数据与替身后端；检查保存、刷新、页签、未保存提醒、认证流程、SSE 断线恢复、危险确认与中文状态，不仅搜索模板字符串。
5. Windows 构建与本机回环冒烟单独记录；真实 Telegram/AI 授权环境验证单独列出，不能用离线 100% 测试通过代替。
6. 最终比较从功能完成度、缺陷、安全、数据兼容、理解成本、依赖与运行表现评分；代码行数和测试数量只作辅助，允许子代理判旧实现某部分更优。
