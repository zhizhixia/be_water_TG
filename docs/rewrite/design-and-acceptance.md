## 2. 重写和不重造的边界

### 推荐实施方式：新应用实现，原版冻结，证据达标后替换

- 按新版需求重新编写业务模型、配置读写、运行控制、三条业务流程、API 和整个 Web 前端，不在原 491 行主循环上继续叠分支。
- 先在项目内持久候选目录完成一条最小闭环，再逐项扩展；通过验收后切换正式入口。
- 沿用已经安装并锁定的 Flask、Waitress、Telethon、OpenAI 兼容客户端、SQLite、python-dotenv、标准库和原生 HTML/CSS/JS，不通过“全量重写”强行引入新技术栈。
- 库与平台能力直接复用；文件安全、迁移和进程锁等平台底层能力允许借鉴已验证实现与测试，但必须逐条符合新契约，不能为改写率降低边界验证。
- 旧 Flet 入口及其专属依赖退出正式运行链，旧版仍在归档可还原。不删除用户材料、历史研究、未知文件或工具配置。
- 不把候选服务指向真实 LOCALAPPDATA；没有单独授权，不对真实数据库执行新 schema 迁移。

### 为什么不建议另换框架

当前主要问题是契约分散、真实路径与测试路径不一致、配置/API/页面脱节，不是 Flask 或原生 JavaScript 无法实现需求。更换前后端框架会多出迁移和依赖工作，却不能自动修复上述问题。本轮不做新的产品/库选型；若实现暴露现有能力无法满足的具体限制，再提出范围明确的选型决定。

## 3. 最小足够架构

```text
中文本地网页
    │ 完整配置、控制、快照、提醒与审计
    ▼
Flask API / SSE
    │ 严格输入校验、本机会话与跨站保护
    ▼
应用控制器（生命周期、认证、配置快照）
    │ 一个后台 asyncio 循环
    ├── 普通参与服务：观察 → 分类/概率 → 候选 → 重评估
    ├── 每日签到服务：上海批次 → 去重 → 明确签到
    └── 抽奖服务：分页扫描 → 识别 → 人工/受限计划
               │
               ▼
统一外发门禁与串行调度
授权 / 时段 / 暂停停止 / 严重安全暂停 / 限流 / 额度
               │
       SQLite 事务预写和结果确认
               │
               ▼
Telegram 适配器（typed InputPeer、真实 SDK 契约）
```

### 职责约束

- **领域模型**：一个群身份、一种消息快照、一套任务结果，不再为普通参与与抽奖分别发明相似但不兼容的 MessageSnapshot。
- **配置**：一个类型明确的模型及统一字段规则，驱动文件加载、API 校验与脱敏响应；不得让网页与文件保存各维护半套字段表。
- **控制器**：负责线程、事件循环、状态迁移、认证和资源清理，不实现文本识别算法。
- **普通参与**：只决定“当前内容是否值得说、说什么、何时到期”，不直接调用 Telegram。
- **签到**：只负责每日任务语义；不作为普通聊天的隐式前置条件。
- **抽奖**：识别与规划是无副作用判断；执行使用不可变原消息引用；人工提醒也是完整结果，不是异常吞掉。
- **调度/门禁**：集中管理对外动作许可、非阻塞 due time 和串行调用；不引入通用工作流引擎。
- **存储**：少量按领域组织的事务方法；保证额度预留、动作状态和扫描检查点的一致性，不暴露让调用者随意拼 SQL 的接口。
- **外部适配器**：所有 Telethon/OpenAI 调用集中在明确边界；只在真实外部输入处做运行期类型/内容验证，不为内部每个调用增加包装层。
- **前端**：配置、快照渲染、事件重连、表单与交互按职责拆少量文件；不用新的框架、控件库或远程字体。

模块最终名称随实现的最小结构确定，禁止为了目录好看预建空类、服务注册器、事件中间件和多层 Repository 包装。

## 4. 数据与接口契约

### 需要持久化的事实

- 群身份与配置别名；授权有效性不能仅靠历史数据库记录推断。
- 群每日普通文本额度、严重暂停、最近有效活动、观察游标、已确认发言。
- 文本外发预留与终态，包括未知结果；候选正文不作为可恢复任务。
- 上海每日签到批次、任务是否进入调用及结果。
- 抽奖扫描游标、扫描健康与失败原因。
- 抽奖发现时间、原消息标识、规范化指纹、截止、来源、动作与结果。
- 抽奖每日群/账号配额、群抽奖冻结、人工提醒、审计。

固定配置目录和 session 文件位置保留。SQLite 使用显式 schema 版本与事务迁移。对无法从旧记录证明的事实保守标记未知，不伪造创建时间、发送成功或账号权限。

### 配置更新语义

- 读接口返回完整非敏感配置及敏感项“是否已设置”。
- 更新接口按显式字段合并；缺项保留，null/空值的清除语义按字段定义，不依赖 Python bool() 宽松转换。
- 以配置版本或同等保护拒绝陈旧页面覆盖更新；保存失败保持原文件。
- 普通参数保存为下次启动快照；页面明确待生效。敏感凭据/授权范围变更必须先停止。
- 签到/抽奖/普通参与的停用动作必须阻止新的外部调用；启用须显式操作，不能由保存其他表单顺带触发。

### 浏览器接口能力

- 健康、完整运行快照、配置读取/更新。
- 开始、暂停、恢复、停止和认证挑战提交。
- 群状态、暂停原因和明确恢复。
- 消息库列表、读取、受控保存与有效消息预览。
- 抽奖待处理、历史、详情、扫描健康、打开原消息、确认恢复冻结、清理预览与确认执行。
- 审计分页和事件订阅。

现有 `/api/start`、`/api/pause`、`/api/resume`、`/api/stop` 等入口可保留以降低耦合；新接口必须由需求驱动。不为内部函数逐一生成 HTTP API。

## 5. 前端设计约束

### 面向的人和操作

操作者打开页面先确认“是否在运行、哪些群有问题、会不会意外发言”，而不是先看累计数字。日常只需开始/暂停/停止和处理少量提醒；设置不应淹没当前状态。

- 领域元素：授权群、等待窗口、待发送候选、签到状态、未知结果、冻结与人工检查。
- 延用当前深色控制台、系统中文字体、低饱和强调色、明确的成功/警告/危险语义。
- 特征组件：群任务状态行，在同一行区分普通参与、签到、抽奖，避免把“一个功能失败”画成“整个群都停止”。
- 不做营销式大数字卡片、装饰性动态图、复杂多面板、无用返回栈。

### 两个待选布局

- **方案 A，任务优先（推荐）**：紧凑固定导航，主区先显示运行状态与群表；人工待办集中列出。独立任务/设置页呈现所有配置。适合长期挂机时快速看异常。
- **方案 B，状态总览**：保留当前概览结构，顶部简短指标，下方群表与待办并排；其余能力分独立页面。更接近旧版，信息密度略高。

在写正式前端前，用相同匿名内容给两套可查看静态原型；原型不能伪称真实运行，不连接账号或后台。用户只需选择布局，不逐项审批颜色、圆角等小细节。

## 6. 纵向实施顺序与完成条件

| 顺序 | 交付结果 | 完成条件与证据 |
|---|---|---|
| 1 | 安全可启动的应用壳 | 隔离目录启动、页面与健康可达、认证和单实例状态可控、无真实外发 |
| 2 | 设置全闭环和数据兼容 | 全字段往返，关闭项不会复活，旧配置/消息库/状态在副本上迁移并恢复 |
| 3 | 一条真实装配的普通参与路径 | Web 配置→控制器→观察/AI或TXT→统一门禁→fake Telegram→SQLite→页面；同时测取消和未知结果 |
| 4 | 长驻调度和每日签到 | 模拟跨窗口/午夜/重启、同群别名、暂停停止及恢复；不重复签到、不阻塞普通参与 |
| 5 | 完整抽奖路径 | 分页/时间边界→识别→callback或固定文本→重读复核→预写→fake动作→结果/提醒→页面 |
| 6 | 任务公平性、异常恢复与前端全部交互 | 慢AI/单群限流/队列等待不拖死其他群；浏览器走完全部入口、错误和重连 |
| 7 | Windows交付和独立比较 | 真实构建/包审计/隔离回环冒烟，归档新证据，才发起只读子代理比较 |

每个结果包含必要实现、相关测试、文档与实际运行证据。没有固定分钟数、没有逐函数测试指标，不为追求 TDD 时间顺序重写已验证成果。安全门禁、幂等和迁移反例优先测试先行，其余遵循清楚的行为验收。

## 7. 共享验收场景

- **V01 配置不漂移**：两个自动功能显式 false，仅读取/保存另一个设置，读回仍 false；字符串布尔拒绝；多行提示词往返。
- **V02 授权不扩大**：同群不同别名只执行一次，单聊/未授权群/移除群零外发；旧队列不绕过新授权。
- **V03 认证可取消**：验证码和两步验证挑战通过网页提交到当前挑战；错误、超时、停止后不可被旧输入复活。
- **V04 自然接话**：问题、讨论、冷场分别按固定随机源决策；同触发只抽一次；话题延续能重新生成；转题、警告取消。
- **V05 AI/TXT闭环**：AI成功、SKIP、非法、超时、TXT缺失/重复；只有确认发送才提交历史；文本不经HTML解释。
- **V06 时间与公平性**：UTC宿主下上海跨日正确；窗口外零外发；慢群不饿死其他群；等待不靠长sleep阻塞。
- **V07 签到至多一次**：当日成功、失败、未知、停机前取消、重启恢复和新增/删除群场景；签到失效不阻塞普通参与。
- **V08 抽奖不漏页**：超过单页上限、页中异常、恢复重试、离线超过一小时、当日置顶和枚举不完整；游标不跳过失败页。
- **V09 抽奖动作白名单**：真实SDK按钮对象；唯一callback、固定顶层文本、固定回复；组合/附加/未知条件一律人工。
- **V10 执行前变化**：发布者降权、实体变化、消息编辑/删除、截止过期、暂停/窗口关闭、冻结/配额变化均阻断旧动作。
- **V11 结果未知**：提交后超时不重试、不退款；冻结范围正确；打开消息不解冻；人工恢复不把未知改成成功。
- **V12 去重和日期**：同消息、跨群指纹、七日边界、相同/不同/未知截止；发现日期与清理边界一致。
- **V13 账本失败**：并发预留、预写失败、外发后确认失败、重启未确认；不突破额度，错误清楚，不能靠吞异常继续。
- **V14 数据迁移**：旧URL键、marked/raw键、已有目标冲突、无效库、重解析点、WAL、失败回滚与恢复；无静默数据丢失。
- **V15 UI真实交互**：所有入口、dirty表单、保存反馈、生效提示、分页、消息文件编辑、恢复、清理、键盘和离线重连。
- **V16 本地安全**：外站Origin/非法Host/无防跨站标识写请求被拒；错误/SSE/日志无敏感内容；自动测试无法连接真实服务。
- **V17 发布**：完整目录EXE、ZIP白名单、运行数据隔离、页面资源、健康、单实例、退出和端口释放。

旧版 512 个测试作为已有证据和行为来源，不强求新版测试数更多。对于实现耦合的旧测试，记录它证明的行为及替代场景；不为了全绿删掉真实回归。

## 8. 最后才执行的新旧比较

### 评价材料

- 同一个获批 `requirements.md`，同一组 V01–V17 场景与独立预期。
- 旧版：含前轮修复的冻结源码、旧测试原始输出、共享场景的真实执行结果。
- 新版：候选源码、对应功能地图、完整测试、浏览器和构建证据、未验证清单。
- 只提供无凭据的源码与匿名证据副本。子代理不得读私有运行数据或修改任一版本，不连接 Telegram/AI。

### 评价方法

| 维度 | 判断依据 |
|---|---|
| 功能完成度 | 按R01–R17对账，不按README宣传或作者摘要 |
| 正确性 | 同口径正例、反例和竞态，引用具体文件/行 |
| 外发安全 | 授权、时段、暂停、信任、配额、幂等和未知结果是否真正约束生产入口 |
| 数据兼容 | 迁移前后事实、冲突处理、回退与信息是否丢失 |
| 前端可用性 | 实际可达入口、中文、保存闭环、错误、断线与键盘，不只比截图 |
| 维护成本 | 理解一项业务需要跳转多少模块、是否重复判断、是否有仅测试可用的第二条实现 |
| 运行开销 | 同匿名负载下的响应、任务公平性和资源行为；没有可重复测量不报提升百分比 |
| 依赖与交付 | 安装/启动/打包步骤、包内容、离线资源、重建与维护负担 |

子代理应先独立识别两版结构和缺陷，再下结论；不提示“新版应该赢”。允许报告某项旧版更简单或更稳。主代理复现关键评价，给出“新版整体更优/仅部分更优/不建议替换”的最终结论，不把子代理摘要直接当验收。
